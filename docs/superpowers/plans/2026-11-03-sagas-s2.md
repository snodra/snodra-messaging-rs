# Sagas S2 (Rust) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The saga model of S1 (sagas, deadlines, the integration toolkit) in the Rust crate `kraken-messaging-rs`, reading and writing exactly the MongoDB shapes of ADR 0021's storage contract.

**Architecture:** The same runtime as S1, in Rust idiom: sagas are registered on `KrakenMessagingBuilder` with a closure-based definition instead of annotations; events reach a local dispatcher that runs the ordinary handlers' transaction (stage 1) and then each saga type's own transaction (stage 2); commands and events a saga emits go to `saga_dispatch` and leave after commit through an ordered relay; deadlines fire from a leased poller; adapters are command handlers made idempotent over `external_calls`.

**Tech Stack:** Rust 2024, tokio, `mongodb` 3 (explicit `ClientSession` transactions), `rdkafka`, `serde_json` (the crate's codec), `reqwest` already present, tests with `testcontainers` (Mongo, Kafka) and the in-process fake hub (`tests/support/fake_hub.rs`).

**Spec:** `kraken-messaging/docs/superpowers/specs/2026-10-31-sagas-design.md` (approved 2026-11-03) and **`kraken/docs/adr/0021-sagas-in-the-library.md`**: its Decision, its storage contract table (binding: collection names, field names, `_id` formats, marker ids, JSON-text fields, indexes, TTLs) and its rulings 1-46 (binding behaviour). The S1 plan `kraken-messaging/docs/superpowers/plans/2026-11-03-sagas-s1.md` and the Kotlin code under `kraken-messaging/kraken-messaging/src/main/kotlin/io/damoreira/kraken/messaging/{saga,deadline,external}` are the reference implementation.

## Global Constraints

- Behaviour equals S1 (ADR 0021 rulings 1-46) unless Rust forces a difference; every difference is an S2 ruling in ADR 0021's new "S2 (Rust)" section with reason and cost if wrong, and a line in the README's divergence list.
- Storage: exactly the contract table. Rust writes no `_class`; it ignores `_class` when reading. Absent fields read as `None`; Rust does not write nulls (skip `None` fields). Dates are BSON datetimes. `state`, the dispatch and failure `payload`, deadline `payload`, `external_calls.reply`/`error` are JSON text (`serde_json::to_string`).
- Saga handlers are **synchronous** closures (the Rust form of S1's "non-suspend" rule: they only record; the runtime does the I/O): `Fn(&mut S, &E, &mut SagaContext) -> Result<(), MessagingError> + Send + Sync + 'static`.
- No new runtime dependency beyond what the crate has (`hmac`/`sha2` for the webhook verifier: `sha2` is present, add `hmac` (pure Rust) only if needed; `subtle` for constant-time compare is acceptable). No C toolchain additions.
- Configuration by environment, mirroring Kotlin's keys with the crate's `_MS` convention: `KRAKEN_SAGAS_ENABLED`, `KRAKEN_SAGAS_MAX_ATTEMPTS`, `KRAKEN_SAGAS_ENDED_RETENTION_MS`, `KRAKEN_SAGAS_DISPATCH_RETENTION_MS`, `KRAKEN_SAGAS_RELAY_POLL_INTERVAL_MS`, `KRAKEN_SAGAS_RELAY_LEASE_MS`, `KRAKEN_SAGAS_RELAY_MAX_ATTEMPTS`, `KRAKEN_SAGAS_RELAY_INITIAL_BACKOFF_MS`, `KRAKEN_SAGAS_RELAY_MAX_BACKOFF_MS`, `KRAKEN_DEADLINES_POLL_INTERVAL_MS`, `KRAKEN_DEADLINES_LEASE_MS`, `KRAKEN_DEADLINES_RETENTION_MS`, `KRAKEN_EXTERNAL_CALLS_LEASE_MS`, `KRAKEN_EXTERNAL_CALLS_RETENTION_MS`; defaults as Kotlin (ADR 0021 / `02-messaging.md` table). External Kafka sources and the webhook secret are configured in code on the builder (a source needs its translator closure anyway).
- The runtime, relay and scheduler start only when at least one saga is registered; `external_calls` indexes only with an idempotent handler; external consumers only with a registered source.
- Commit messages end with exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Docker-backed test runs go through the workspace lock wrapper.

## Builder rulings (planning; each goes into ADR 0021 "S2 (Rust)" with cost if wrong)

- **S2-R1. Registration API** (no annotations): `KrakenMessagingBuilder::saga::<S>(name: &'static str, define: impl FnOnce(SagaDefinition<S>) -> SagaDefinition<S>)` with `S: Serialize + DeserializeOwned + Default + Send + 'static`; `SagaDefinition<S>`: `.start_on::<E>(key: &'static str, value: fn(&E) -> Option<String>, handler)`, `.start_new_on::<E>(handler)` (forceNew), `.on::<E>(key, value, handler)`, `.on_header::<E>(key, header: &'static str, handler)`, `.ending()` (marks the handler just added as `@EndSaga`), `.on_deadline::<P: DeserializeOwned>(name: &'static str, handler: Fn(&mut S, Option<P>, &mut SagaContext) -> Result<(), MessagingError>)`, `.on_command_failed(handler: Fn(&mut S, &SagaCommandFailed, &mut SagaContext) -> Result<..>)` (ADR ruling 27: routed by `sagaId`, no association). Handlers of one event type run in registration order (Rust has it; Kotlin's method-name order was a reflection limit: divergence recorded).
- **S2-R2. Startup checks** at `start()`: a saga with no start handler; duplicate saga names; a fresh `S::default()` that does not round-trip through `serde_json` (to and from the stored JSON text); `.ending()` with no preceding handler. Errors name the saga and the handler (`<saga>.<event type>`).
- **S2-R3. `SagaContext`**: `saga_id()`, `associate_with(key, value)`, `remove_association_with(key, value)`, `end()`, `send<C: Command>(&C, routing_key: Option<&str>) -> Result<(), MessagingError>`, `publish<E: Event>(&E, key: Option<&str>) -> Result<..>`, `schedule_after<P: Serialize>(Duration, name, Option<&P>) -> String`, `schedule_at<P>(SystemTime, name, Option<&P>) -> String`, `cancel(id)`, `cancel_all(name)`, `message() -> &MessageContext`. Saga handlers cannot reach the buses (they get no `Sender`/`EventBus`): the Rust form of ruling 32 is by construction; a closure that captures a `Sender` is documented as forbidden (it would send inside the saga's transaction).
- **S2-R4. `SendOptions.headers: HashMap<String, String>`** (new, default empty), carried to `Request.headers` and to a local handler's `MessageContext.headers`; reserved names refused as in Kotlin (`authorization`, `traceparent`, `tracestate`, `correlation-id`, `correlationId`).
- **S2-R5. Local short-circuit for saga commands**: the crate sends every command through the hub today. The relay uses a `RawCommandSender` that delivers a command type this instance handles to its own handler directly (no hub: spec decision 5), and every other type through the hub (`Sender::send_raw`), with ADR ruling 34 (`NO_HANDLER` transient through the hub, permanent locally) and ruling 29 (`RetryPolicy::NONE`).
- **S2-R6. Test fixture** `kraken_messaging_rs::saga::testing::SagaTestFixture` behind a cargo feature `testing` (in-memory ports, the real runtime), since the crate has no separate test-kit crate.
- **S2-R7. Metrics**: the crate has no registry (P5b ruling): counters and gauges as accessors `KrakenMessaging::saga_stats() -> SagaStats` with the same names and labels as the Kotlin meters.
- **S2-R8. Example**: service-c (Rust) gets its own saga with its own types (`examples.PrintBanner`, `examples.PollBannerJob`, events `examples.BannerPrinted`, `examples.BannerFailed`): command types are single-owner, so it cannot reuse service-b's `PrintPostcard`. The fake printer gains a per-request reply target (webhook URL or reply topic) so banner jobs never reach service-b's saga; service-c gains a small HTTP endpoint for the webhook (an example-only dependency); the dev ACL (`kraken/infra/scripts/dev-hub-pki.sh`) lets service-c handle the two new command types (S1 lesson: the secure sandboxes refuse unknown handled types).

## Review Focus

1. A Rust service's documents follow the contract exactly (field names, types, `_id` formats, JSON-text fields, absent-not-null) and documents in the Kotlin shape (with `_class`) are read correctly. → Task 2 contract tests with JSON fixtures written from the ADR table.
2. An event that matches a live instance and a start handler is handled once, by the instance; two concurrent events for one instance both apply, never interleaved. → Task 5.
3. A crash between commit and dispatch, and between dispatch and mark: re-sent with the same `idempotency-key`, the idempotent adapter's body runs once. → Tasks 6 and 9.
4. A failing ordinary handler does not hide the event from sagas (ruling 26); one saga type failing forever does not block another (ruling 1). → Tasks 4 and 5.
5. A hung adapter does not hold back other sagas' dispatch, and its lease is renewed while it runs (ruling 30). → Task 6.
